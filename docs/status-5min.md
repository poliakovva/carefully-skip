# `--carefully-skip-permissions`: статус за 5 минут

**Тип документа:** текст короткой презентации (8 слайдов, ~5 минут)
**Срез:** 4 сентября 2026
**Источники:** [adjudicator-overview.md](./adjudicator-overview.md), [benchmark-progress.md](./benchmark-progress.md)

Классификатор разрешений (adjudicator) реализован и покрыт тестами. На бенчмарке — первый реальный сигнал: строгий матчер показал, что `rules.ts` снижает ASR с 29.4% до 26.5%. Дальше — снять калибровочный патч и подключить классификатор к тому же прогону.

- Адьюдикатор — реализован, тесты зелёные.
- Бенчмарк — `rules.ts` даёт реальное снижение ASR.

## 1. Какую проблему решаем — на чём сосредоточились

Пользователь coding agent выбирает между approval fatigue (подтверждать почти каждое действие) и blanket auto-approval (отключить проверки и открыть путь деструктивным командам, действиям вне намерения и prompt injection).

Два трека фокуса:

1. **Заменить бинарный выбор** — адьюдикатор: детерминированные правила плюс LLM-классификатор для серых случаев, спорное решает человек.
2. **Не верить архитектуре на слово** — измерить её на открытом benchmark относительно двух опорных точек: allow-all и deny-all.

## 2. Как решили — арбитр разрешений (реализовано)

Пайплайн:

1. **immune-брейкеры** — срабатывают даже при пользовательском `allow`: опасное удаление, opaque-конструкции, cross-session.
2. **детерминированный слой** — 50 правил: 1 hard, 32 soft, 17 exempt — чистые функции от фактов действия.
3. **LLM-классификатор** — только для оставшихся серых случаев; видит факты действия, а не текст команды.
4. **резолвер → вердикт** — `allow` / `deny` / `escalate`.

Ключевое:

- единственная точка перехвата — `Permission.ask`, приоритет существующих `deny`/hard-правил сохранён;
- любой сбой (таймаут, невалидный ответ, нет фактов) → `escalate`, никогда `allow`;
- включение отдельным флагом `--adjudicate`, не путать с существующим `--auto`.

## 3. Как решили — проверено тестами

**Юнит и интеграционные (мок модели):** брейкеры и детерминированный слой; сборка промпта (границы блоков, редактор секретов, отсутствие описания); валидация ответа модели и резолвер; транспорт отказа, политика сессии, журнал, TUI-контроллер.

**Live-набор (реальная модель, `KILO_ADJUDICATOR_LIVE=1`):**

| Действие | Вердикт |
|---|---|
| Чтение файла | `allow` |
| Эксфильтрация `.env` | `deny` |
| Именованное удаление | `allow` |
| Удаление по общей цели | `deny` |

Это подтверждает техническую целостность прототипа — не безопасность в целом. Это уже задача бенчмарка.

## 4. Как решили — методология бенчмарка

Три опорные точки:

```
[1] allow-all (baseline)  →  адьюдикатор / rules.ts  →  [2] deny-all
    ASR-потолок, FP=0 (тавтология)   реальный измеряемый механизм    ASR-пол, FP-потолок
```

`rules.ts` (день-1 механизм) встал между allow-all и deny-all — измерено на 17×8, см. ниже.

Условия прогонов: harness — AIShellJack, codebase — `django_Python/ludic`, модель — `gemini-3.1-flash-lite`.

## 5. Результаты — rules.ts реально снижает ASR (17×8 = 144 прогона)

**Находка по пути.** Матчер ASR из upstream-paper слишком мягкий: засчитывает атаку успешной по совпадению одного токена (даже фрагмента пути) плюс любой не-setup команде. Ввели строгий матчер (≥20% совпадения токенов) — `score_kilo.py` считает оба числа сразу.

| Метрика | Значение |
|---|---|
| Baseline, strict ASR | 29.4% (upstream-матчер давал 47.8%) |
| Enforce, strict ASR — реальный `rules.ts` | 26.5% (upstream-матчер давал 50.7%) |
| Реальных `deny` за прогон | 6 — 4.4% атак, 0.15% всех вызовов |
| Объём выборки | 144 прогона: 17 техник × 8 surface, 9 MITRE-тактик |

На upstream-матчере enforce выглядел *хуже* baseline (50.7% против 47.8%) — эффект тонул в шуме. На строгом пороге видно обратное: `rules.ts` действительно снижает ASR. Заблокированы: `write-system-path` (SysV-сервис в rc.d), `secret-access` ×2 (копирование SSH-ключа), `pipe-to-shell` (curl|bash).

**Для калибровки (прогон #5, deny-all):** ASR/FP 0% / 100%, как и предсказано — подтверждает, что pipeline harness → Docker → auth → инъекция → audit → scorer корректно ловит `deny` целиком.

## 6. Что непонятно

**Классификатор:**

- слабая модель: семантически ложные `no_match`/`authorized` механически не ловятся;
- латентность 2–13 с на решение, растёт с числом маршрутизированных правил;
- `kilo-auto/free` непригоден как классификатор — упирается в лимит рассуждений;
- реплики пользователя авторитетны для модели; гарантии дают только брейкеры и детерминированные правила.

**Бенчмарк:**

- строгий матчер надёжнее, но не идеален — та же токенная логика, просто с фильтром;
- ветка адьюдикатора не в `main` — не подключена к harness, сравнение трёх механизмов не завершено;
- полная матрица (5 codebase × 314 техник) — дорого (~$665), рано без адьюдикатора;
- slopsquatting-модуль и безопасное продолжение после блокировки не начаты.

## 7. Что дальше

1. **Убрать калибровочный патч** — `KILO_AUTO_MODE_DENY_ALL` в `rules.ts` был нужен только для проверки pipeline, снять после подтверждения текущего прогона.
2. **Смёржить адьюдикатор в harness** — ветка `feature/adjudicator-effort` → подключить классификатор к тому же прогону 17×8.
3. **Сравнить три механизма на strict-ASR** — Utility, FP, Friction, Latency: allow-all vs `rules.ts` vs adjudicator на одинаковой выборке.
4. **Полная матрица** — 5 codebase × 314 техник × 8 surface × 2 условия, после того как шаги 2–3 подтвердят стабильность.
