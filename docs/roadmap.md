## 0. Стратегия (прочитать перед стартом)

Кейс сформулирован широко — **побеждает не широта, а глубина + честные цифры**. Рекомендуемый фокус:

1. **Auto mode** — перехват команды агента до выполнения, классификация `allow / ask / deny`.
2. **Один архитектурно injection-неуязвимый контроль** (обязательное требование #2) — детерминированный слой в execution-layer, до которого инъекция из контекста физически не доходит.
3. **Slopsquatting-модуль** — проверка npm/pip-пакета внутри агента, до установки, с защитой от zero-day.
4. **Бенчмарк + 5 метрик** — это главный измеримый результат (ASR↓, Utility↑, FP↓, Friction↓, Latency↓).

Всё остальное (downgrade-атаки, эксфильтрация, наблюдаемость) — в бэклог. **Лучше 3 контроля с честным бенчем, чем 8 «на словах».**

### Ключевая архитектурная идея (для требования «неуязвимость к prompt injection»)

Политика `allow/deny/ask` живёт **не в промпте LLM**, а в отдельном **policy-движке на перехвате tool-call** (deny-first, deny всегда бьёт allow). Инструкции из `SKILL.md`/README/MCP не могут ослабить правило, потому что они не участвуют в решении — решает детерминированный код над командой. LLM-классификатор — только **вторая линия** для неоднозначных случаев, и он никогда не может понизить вердикт `deny`.

```
tool call → [1. deny-first policy engine (детерм., injection-immune)] → deny? стоп
          → [2. slopsquatting check при install]                     → risk? ask/deny
          → [3. LLM-классификатор (Llama Guard-подход) для «серых»]   → ask/allow
          → [sandbox/dry-run при необходимости] → выполнение → лог/трейс
```

## День 1 — Разведка, модель угроз, перехват + deny-first движок

**Цель:** зафиксированный scope, работающий перехват команд, первый детерминированный контроль.

- **PM:** составить **модель угроз** (черновик README): таблица «угроза → вектор → наш контроль → гарантия (always / best-effort)». Разобрать датасет кейсодателя (~20 задач + ~20 атак), разметить атаки по типам (slopsquatting, prompt injection в SKILL.md, неосторожные `rm -rf`/DROP, эксфильтрация). Зафиксировать определения 5 метрик и как их считаем.
- **AI Eng 1:** развернуть Kilo Code, найти точку перехвата tool-call/exec, сделать **hook** (лог каждой команды до выполнения) и сразу поверх — **deny-first policy engine** (детерминированные правила: `rm -rf /`, `curl|sh`, доступ к `.env`/секретам, `DROP DATABASE`, запись вне рабочей директории). Это и есть injection-immune контроль. Изучить #9138.
- **AI Eng 2:** собрать **бенчмарк-харнесс** — прогоняет N задач + M атак через агента, считает ASR / Utility / FP / Friction / Latency, выдаёт таблицу. Самый важный инструмент: без него нельзя итерировать. Референс — [Llama Guard](https://arxiv.org/abs/2312.06674)/[NeMo Guardrails](https://github.com/NVIDIA-NeMo/Guardrails).

**Готово к концу дня:** перехват + deny-first работают; **бенчмарк даёт baseline-цифры** (без защиты vs с deny-first). С этого момента любое изменение меряется.

## День 2 — LLM-классификатор + slopsquatting-модуль

**Цель:** покрыть «серую зону» и закрыть требование про slopsquatting (zero-day, до установки).

- **AI Eng 2:** **slopsquatting-модуль** — вызывается на `npm/pip install <pkg>` ДО установки. Zero-day эвристики: возраст пакета, число загрузок, дистанция Левенштейна до популярных имён (typo/тайпсквоттинг), отсутствие в lock-файле, репутация мейнтейнера. Ориентир — [Depscope](https://depscope.dev/). Возвращает risk-score → `ask`/`deny`.
- **AI Eng 1:** **LLM-классификатор** для неоднозначных команд (Llama Guard-подход: таксономия рисков). Важно: он может только **эскалировать** (`allow→ask`), но не понижать `deny`. Прогнать на устойчивость к инъекциям.
- **PM:** расширить датасет атак (multi-step, «неявная» установка пакета), критерии «ущерб засчитан» (ASR) и «задача успешна» (Utility); тест-кейсы на approval fatigue (для Friction/FP).

**Готово к концу дня:** 3 контроля работают вместе; повторный прогон показывает **ASR↓ относительно baseline**.

## Целевые метрики (ориентир)

- **ASR ↓** — главная. Показать заметное падение vs baseline (без защиты).
- **Utility ↑** — держать ≥ 90% легитимных задач (иначе защита «за счёт неработы»).
- **FP ↓ / Friction ↓** — минимум лишних блокировок и вопросов человеку.
- **Latency ↓** — проверка не должна быть дольше самого действия (дешёвые правила → дорогой LLM только на «серых»).

## Что режем первым (MoSCoW)

- **Must:** deny-first policy engine, бенчмарк-харнесс, slopsquatting, метрики, README-модель угроз.
- **Should:** LLM-классификатор, продолжение после блокировки, тюнинг FP/Friction.
- **Could:** allow/deny/ask пресеты, downgrade-защита, наблюдаемость/трейсинг, исследование approval fatigue, PR в upstream.
- **Won't (в этот раз):** полноценный sandbox-рантайм, защита от эксфильтрации через сеть, мультиагентные сценарии.

## Главные риски

- **Погружение в Kilo Code internals** дольше плана → заложить День 1 целиком на перехват; если к концу Дня 1 hook не работает — эскалировать/упростить точку интеграции.
- **Нет ранних цифр** → бенчмарк-харнесс обязателен ко Дню 2, иначе нечем доказывать результат.
- **«Гардрейл на промпте»** легко обходится → injection-immune контроль должен быть детерминированным кодом над командой, а не инструкцией модели.
